Mandate flow: first commit against today's main

Comparing 299bca6 (20 Nov, the hackathon base) with 521a378 (24 Nov). 39 commits, 130 files, about 14,900 lines added.

The starter had one control point: the gateway checked a signed mandate, then forwarded the call to a data server that trusted anyone. Today the gateway still makes the decision, but it is no longer the only thing between an agent and the data. The data servers check a signed grant for every call, a separate issuer service holds the signing key and mints narrower mandates on a person's approval, and every call leaves a signed record. The request shape of POST /tools/call has not changed.

Before: one check, then trust

After: every hop is scoped, and asking for more is a path

What changed, and why

ChangeFirst commitNowReasoning
Scope checksQuestions 3 to 5 No row limit. Paths compared as typed. The first scope entry that matched the tool decided the call. At most 100 rows and no empty search (TOO_MUCH). Paths normalised before comparing. One entry must accept every argument it constrains. The starter failed questions 3 to 5: a bulk export, a path spelled differently, and a mandate covering two schools. The eval is now 32/32 per the commit log.
Clearance and slicesQuestions 6 and 15 One server holding every column. Scope was the only limit. A clearance claim (1 to 4) checked before scope. Three narrow servers, each able to read only one level. A scope written too wide by mistake should not reach sensitive data. Checking clearance first means no shape of scope entries routes around it.
Graded pupil dataQuestions 6, 9, 15 Any allowed call returned whole rows, ethnicity and care status included. Results stripped to the mandate's clearance (level 2 if it has none). Level 4 reads are held call by call. A search cannot select rows by a hidden value. A live check found a no-clearance mandate returning a named pupil's special category data. A search for "ASIA" also returned exactly the pupils of that ethnicity after stripping.
Tool grantsGateway to tool hop The MCP server answered anyone. Going to :8080 was a known hole. Each forwarded call carries a grant bound to server, tool, exact arguments, schools, pupils, level and row cap. Servers refuse calls without one and filter their own output. The gateway should not be a single point of failure. A gateway bug, or a caller who reaches a server directly, gets no more than one grant allows.
Scope requests and the issuerQuestions 7, 9, 10 STEP_UP returned 202 and stopped. The issuer key sat in the gateway container. The agent asks through grants.request. A person (or a supervising agent within its own scope) approves. The issuer mints a child mandate for the same key. A held call goes through once. A refusal needs a safe next step, or people over-grant up front. Moving the key out means a compromised gateway cannot mint. Children die with their parent and with the supervisor that approved them.
Fewer promptsRun reuse, batch release Not applicable. An approval still valid in the same run is reused. Up to 50 held calls can be released by one approval, each still once. Asking a person again for what they approved minutes ago, or 25 times for one job, trains them to approve without reading.
Audit trailQuestions 14 and 16 None. A comment marked where teams could add one. One signed, hash-chained event per call, refusals included. An allowed result is withheld (503) if its event cannot be written. Reading the log is itself a mandated call. The person who granted a mandate should be able to see what it received. Events hold identifiers and levels, never values, so the log is not a second copy of the data.
Safe countsQuestion 8 aggregate counted rows and suppressed nothing. Counts are of distinct pupils, groups under 10 are dropped, small counts hidden, everything rounded to 5. Identifier columns are refused. A count filtered to one pupil named that pupil's ethnicity through the starter gateway.
Run budgetsQuestion 11 Each call judged alone. Per-mandate budgets for distinct pupils and calls, shared by child mandates. Ceilings per key and per source. Alerts for mandates with no budget. Many small allowed calls add up to a bulk export. The source ceiling runs before signature work so a forged flood stays cheap to refuse.
Deployment hardeningDay 2 30 s grace on expiry. Demo routes always on. All ports published. Malformed mandates could raise a 500. Expired means expired. Demo off unless enabled. Only the gateway is public. Anything unparseable is a MANDATE_MALFORMED denial. The demo mints and revokes with no login, and a leaked issuer key costs 50 points on Day 2.
MCP shim and wallet The agent held its key and mandate and signed requests itself. A local MCP server holds both, picks the narrowest mandate that covers a call, and keeps approved mandates out of the agent's view. Claude Code had no way into the scope-request loop, and an agent that never sees a credential cannot leak it.

What stayed the same

  • The POST /tools/call body and its signing input.
  • The mandate as an EdDSA JWT bound to the agent's key, with the trusted list and signed status list for revocation.
  • The order of the first three checks: mandate, proof of possession, then scope.
  • The synthetic data and the demo walkthrough.

Still open in the current design

  • An approver is a key file per person, and their ceiling is a JSON file. Neither is SSO or a real entitlement source.
  • Pupil IDs are the same on every server, so a name from directory can be joined to an approved special record.
  • The nonce replay set is in memory, per process.
  • The issuer and cli issue both write status_list.json with no lock between them.
  • Path normalisation is lexical, which holds only while the data directory has no symlinks.
  • One approval is enough even for special category data or a write, and only the principal can give it.
