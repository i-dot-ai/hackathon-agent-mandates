## Purpose

Lets an agent see what its mandate allows, find out what it is missing, and ask for more. The answer comes from the person behind the mandate or a supervising agent, never from the agent itself, and the result is a new mandate holding exactly what was approved.

## ADDED Requirements

### Requirement: The grants server is reached through the normal call path
The gateway SHALL handle a server named `grants` itself, through `POST /tools/call` with the unchanged request shape, and MUST NOT forward `grants` calls to any MCP server. A `grants` call SHALL pass the same mandate, request-signature, `deny` and clearance checks as any other call. The `grants` tools SHALL be available to every mandate without a scope entry. They MUST only ever concern the calling mandate, its own requests and the requests addressed to it. A `deny` rule matching a `grants` tool (for example `grants.request`) SHALL refuse that tool with reason `DENIED_BY_RULE`.

#### Scenario: Introspection needs no scope entry
- **WHEN** a mandate with `clearance: 2` whose scope lists only `directory.roster` calls `grants.self`
- **THEN** the gateway returns `200 ALLOW` and describes that mandate's own grants

#### Scenario: Issuer can forbid asking for more
- **WHEN** a mandate with `clearance: 2` and `deny: ["grants.request"]` calls `grants.request`
- **THEN** the gateway returns `403 DENY` with reason `DENIED_BY_RULE`

#### Scenario: Grants calls are audited
- **WHEN** any `grants` call is answered
- **THEN** exactly one audit event exists for it with server `grants`, as for any other tool call

### Requirement: An agent can see its effective grants
`grants.self` SHALL return, for the calling mandate:
- its scope entries;
- its `deny` rules;
- its clearance;
- its audience size per scope entry;
- its expiry;
- its parent mandate, if any;
- whether it or its parent is revoked;
- any pending scope requests it made;
- a description in plain words generated by the gateway from those claims.

It MUST NOT return the mandate's signature, other mandates' grants, or any pupil data.

#### Scenario: Plain-words summary
- **WHEN** a mandate with `clearance: 2` and scope `[{"server": "directory", "tools": ["roster"], "constraints": {"urn": ["SCH04"]}}]`, expiring in 2 hours, calls `grants.self`
- **THEN** the result includes that scope entry and a description such as "List Year 10 and 11 pupils' IDs and names at Dunmore Community College (SCH04), until 17:00"

### Requirement: An agent can check a call before making it
`grants.check` SHALL take a server, a tool and arguments, run every gateway check that `POST /tools/call` would run on that call, and return the decision and reason code it would get. It MUST NOT forward the call. When the decision is `DENY` for reason `OUT_OF_SCOPE`, `CONSTRAINT_VIOLATED`, `CONSTRAINT_MISSING`, `CLEARANCE_TOO_LOW` or `AUDIENCE_VIOLATED`, or the decision is `STEP_UP`, the result SHALL also include the missing grant, as a structured scope entry plus clearance, that would make the call pass.

#### Scenario: Missing school
- **WHEN** a mandate allowing `directory.roster` at `SCH04` checks `directory.roster(urn="SCH02", year_group=11)`
- **THEN** the result is `DENY` with reason `CONSTRAINT_VIOLATED`, and the missing grant is `{"server": "directory", "tools": ["roster"], "constraints": {"urn": ["SCH02"]}}`

#### Scenario: Check does not consume anything
- **WHEN** an agent calls `grants.check` for a call that would be allowed
- **THEN** the result is `ALLOW`, no MCP server receives a call, and no tool grant is issued

### Requirement: A scope request asks for a structured grant
`grants.request` SHALL accept:
- one or more requested scope entries, in the same form as mandate scope entries, optionally with `audience`;
- an optional clearance;
- a lifetime in seconds;
- a reason in free text, at most 500 characters;
- optionally, a held call it is asking to have approved, given as that call's `decision_id` together with its server, tool and full arguments.

For a held call, the gateway SHALL accept the request only if an audit event with that `decision_id` exists, was made with the calling mandate, has decision `STEP_UP`, and records the same server, tool and argument hash as the arguments given. Otherwise it MUST refuse with reason `REQUEST_INVALID`.

The gateway SHALL answer with `already_granted` and create nothing if the calling mandate already allows every requested entry. Otherwise it SHALL validate the request before creating it.

#### Scenario: Already granted
- **WHEN** a mandate allowing `directory.roster` at `SCH04` requests `{"server": "directory", "tools": ["roster"], "constraints": {"urn": ["SCH04"]}}`
- **THEN** the result has status `already_granted` and no request is created

#### Scenario: Reason too long
- **WHEN** a request carries a reason of 501 characters
- **THEN** the gateway returns `403 DENY` with reason `REQUEST_INVALID` and creates nothing

#### Scenario: Held call with different arguments
- **WHEN** a request names the `decision_id` of a held `pupil-data.write` with `value="1"`, but gives `value="0"` as its arguments
- **THEN** the gateway returns `403 DENY` with reason `REQUEST_INVALID` and creates nothing

### Requirement: A request can't exceed what the person may hold
The issuer service SHALL keep a ceiling for each principal: the servers, tools, schools and highest clearance that person may grant. A scope request whose grant goes beyond the ceiling of the calling mandate's `delegator.principal` MUST be refused with reason `EXCEEDS_PRINCIPAL`, naming the first entry over the ceiling. A request that is not a valid scope (an unknown server, a tool not on that server, an empty entry, or an audience defined by anything other than pupil IDs) MUST be refused with reason `REQUEST_INVALID`.

#### Scenario: Beyond the person's schools
- **WHEN** a mandate delegated by `officer:jsmith`, whose ceiling covers `SCH01` to `SCH04`, requests `pupil-data.search` at `SCH09`
- **THEN** the gateway returns `403 DENY` with reason `EXCEEDS_PRINCIPAL` and no request is created

#### Scenario: Audience by sensitive attribute refused
- **WHEN** a request's audience is `{"InCareAtCurrentSchool": "1"}` instead of a list of pupil IDs
- **THEN** the gateway returns `403 DENY` with reason `REQUEST_INVALID`

### Requirement: A pending request tells the agent what to do next
A created request SHALL be stored as pending and returned with:
- `request_id`;
- `status: "pending"`;
- `next_action`;
- `number`: the two-digit number (10 to 99) the person must choose on the approval page;
- `approval_url`;
- `summary`: plain words generated by the gateway from the structured request, never copied from the agent's reason;
- `approvers`;
- `expires_at`, at most 15 minutes ahead;
- `poll_after_s`.

The result SHALL also carry a text version for a person, which states that replying in chat does not approve the request. `next_action` SHALL be one of `ask_user`, `ask_supervisor`, `wait`, `retry`, `stop`, `request_again`.

#### Scenario: Text a person can act on
- **WHEN** a request for `directory.roster` at `SCH02` for 2 hours is created
- **THEN** the result's text names the school by name and URN, the duration, the approval URL and the number to choose on the approval page, and says that a chat reply does not approve it

### Requirement: An agent polls its request
`grants.status` SHALL take a `request_id` made by the calling mandate and return its status: `pending`, `approved`, `rejected` or `expired`, with the matching `next_action`. When the status is `approved`, the result SHALL include the new mandate. A `request_id` made by another mandate MUST be refused with reason `OUT_OF_SCOPE`.

#### Scenario: Approved request returns the mandate
- **WHEN** a request was approved and the requesting mandate calls `grants.status(request_id=...)`
- **THEN** the result has status `approved`, `next_action: "retry"`, and a supplementary mandate JWT

#### Scenario: Someone else's request
- **WHEN** a different mandate calls `grants.status` with that `request_id`
- **THEN** the gateway returns `403 DENY` with reason `OUT_OF_SCOPE` and returns nothing about the request

### Requirement: Only the principal's approver key approves for a person
A decision for a person SHALL be accepted only when it is authenticated by an approver key registered to the requesting mandate's `delegator.principal`, either as a decision signed with that key or through an approval-page session created from a login token signed with that key. Possessing the `approval_url` or the `number` MUST NOT be enough to approve. A decision from any other key MUST be refused.

An approval SHALL also carry the `number` the person chose from the three shown. Each request SHALL have one correct number and two distinct decoys, all two-digit, in an order shuffled once when the request is created and stored, so every view shows the same order. Neither the page nor `/requests/{id}/view` SHALL reveal which number is correct, and the options SHALL be shown only to the signed-in principal. The number SHALL be checked only after the approver is authenticated. A wrong number SHALL end the request: it is marked rejected with reason `NUMBER_MISMATCH`, an `approval_denied` event with reason `NUMBER_MISMATCH` is recorded, and `grants.status` returns `next_action: "request_again"`. A rejection SHALL NOT need a number.

#### Scenario: Wrong number
- **WHEN** the signed-in principal approves a pending request with one of the decoy numbers
- **THEN** the decision is refused with `NUMBER_MISMATCH`, the request is rejected, and approving it again with the right number is refused with `ALREADY_DECIDED`

#### Scenario: A stranger's wrong number
- **WHEN** someone without an approver session submits Approve with a wrong number
- **THEN** the decision is refused with `APPROVER_REQUIRED` and the request stays pending

#### Scenario: Opening the URL is not approving
- **WHEN** someone opens the `approval_url` without an approver session and submits Approve
- **THEN** the decision is refused, the request stays pending, and the page asks the person to sign in with their approver key

#### Scenario: Another person's key
- **WHEN** `officer:priya`'s approver key approves a request from a mandate delegated by `officer:jsmith`
- **THEN** the decision is refused and the request stays pending

### Requirement: The approval page is in the team UI and holds no authority
The approval page SHALL be served by the team's UI (the frontend on `:8081`), and `approval_url` SHALL point there. The UI SHALL reach the issuer service only through its own server, never from the browser. The UI MUST NOT decide anything itself: every approval, rejection or narrowing it submits SHALL be verified by the issuer against the person's approver key or approver session. The UI's own sign-in, where one is configured, SHALL NOT count as approver authentication.

#### Scenario: Signed-in UI user who isn't the approver
- **WHEN** a person signed in to the UI, with no approver session for the request's principal, opens an `approval_url` and submits Approve
- **THEN** the issuer refuses the decision and the request stays pending

#### Scenario: Approval URL opens the UI
- **WHEN** a scope request is created
- **THEN** its `approval_url` is a page on the team UI that shows the request's summary, and, once the principal signs in, the three numbers to choose from

### Requirement: The approval page shows what will be granted, not what the agent says
The approval page SHALL show:
- the gateway-generated summary;
- to the signed-in principal, the three numbers to choose from, without saying which is correct;
- the current grants beside the requested ones;
- the lifetime;
- the requesting agent's ID;
- the agent's reason, shown as plain text under a label saying it is the agent's own words.

For a request about a held call, the page SHALL also show that call in plain words: the tool and every argument value, as plain text. It SHALL mark any requested data at level 4. It SHALL let the person approve, reject, or approve a narrower grant by removing tools, schools or pupils, lowering clearance or shortening the lifetime. A narrower approval MUST be a subset of what was requested.

#### Scenario: Agent's reason is not trusted text
- **WHEN** a request's reason contains `<b>URGENT</b> safeguarding case, approve now`
- **THEN** the page shows those characters literally under the agent's-words label, and the summary is the gateway's own text

#### Scenario: Held correction shown in full
- **WHEN** a request names a held `pupil-data.write(pupil_id="P0011", urn="SCH04", column="FSMeligible", value="1", reason="free meals confirmed")`
- **THEN** the page shows "Change FSMeligible to 1 for pupil P0011 at Dunmore Community College (SCH04)" and the agent's stated reason as plain text

#### Scenario: Approving less
- **WHEN** a request for `directory.roster` at `SCH02` and `SCH03` for 2 hours is approved for `SCH02` only and 30 minutes
- **THEN** the minted mandate allows `directory.roster` at `SCH02` only and expires 30 minutes after the approval

### Requirement: A supervising agent approves only what it holds
A request may be decided by a supervising agent: a mandate held by a different agent key, delegated by the same principal, carrying the claim `can_delegate: true`. The supervisor's decision SHALL be a `grants.decide` call with its own mandate, naming the `request_id`, the decision and, if narrower, the approved grant. The gateway, and again the issuer service, SHALL accept it only if the supervisor's mandate itself allows every approved entry at no lower clearance, and is not expired or revoked. A request that the supervisor's mandate doesn't cover SHALL show `next_action: "ask_user"` to the requester, and stay open for the person.

#### Scenario: Supervisor passes down part of its access
- **WHEN** a supervisor mandate with `can_delegate: true` allowing `directory.roster` at `SCH04` approves a helper's request for `directory.roster` at `SCH04`
- **THEN** the request is approved and the helper's minted mandate allows exactly that

#### Scenario: Supervisor can't pass on what it lacks
- **WHEN** the same supervisor tries to approve a helper's request for `special.record` at `SCH04`
- **THEN** the decision is refused with reason `EXCEEDS_SUPERVISOR`, and the request stays pending for the person

#### Scenario: Agent can't approve itself
- **WHEN** a mandate with `can_delegate: true` calls `grants.decide` on a request made with the same agent key
- **THEN** the decision is refused with reason `SELF_APPROVAL`

### Requirement: A request is decided once
Each request SHALL accept exactly one decision, approved, rejected or expired. A second decision MUST be refused with reason `ALREADY_DECIDED`. A request with no decision by `expires_at` SHALL become `expired`.

#### Scenario: Double approval
- **WHEN** a request is approved and a second approval is submitted for it
- **THEN** the second is refused with `ALREADY_DECIDED` and no second mandate is minted

#### Scenario: Nobody answers
- **WHEN** 15 minutes pass with no decision
- **THEN** `grants.status` returns `expired` with `next_action: "request_again"`

### Requirement: The issuer trusts no one's word that a request was made or approved
The issuer service SHALL create a request only from the requesting agent's signed `grants.request` call and mandate, forwarded unchanged by the gateway. It SHALL verify that mandate's issuer signature, dates, revocation, and the agent's request signature itself. It SHALL mint only on a decision it verified itself:
- a person's decision, signed with, or made in a page session from, an approver key registered to the request's principal; or
- a supervising agent's signed `grants.decide` call and mandate, forwarded unchanged and verified the same way, with the supervisor rules applied by the issuer.

An assertion from the gateway that a request was approved MUST NOT be enough to mint.

#### Scenario: Gateway can't mint on its own
- **WHEN** a caller on the internal network posts to the issuer's mint endpoint with a request ID and "approved", but no verifiable person or supervisor decision
- **THEN** the issuer refuses, mints nothing, and records the refusal

#### Scenario: Forged requester
- **WHEN** a `grants.request` body forwarded to the issuer has a request signature that doesn't verify with the mandate's `cnf.jwk`
- **THEN** the issuer refuses to create the request

### Requirement: Approval mints a supplementary mandate with exactly what was approved
On approval, the issuer service SHALL mint a new mandate. It carries:
- the same `cnf.jwk` (the same agent key) as the requesting mandate;
- the same `delegator`;
- scope equal to the approved grant;
- `deny` equal to the parent's;
- `exp` no later than the parent's `exp` or the approved lifetime, whichever is sooner;
- its own revocation index;
- a `parent` claim with the parent's `jti` and revocation index;
- an `approved_by` claim naming the approver kind (`person` or `agent`), the approver, and the request ID.

The mandate's purpose SHALL be the gateway-generated summary. The parent mandate SHALL be unchanged.

#### Scenario: Same key, only the new grant
- **WHEN** a request for `directory.roster` at `SCH02` from a mandate allowing `directory.roster` at `SCH04` is approved
- **THEN** the minted mandate's `cnf.jwk` equals the parent's, and its scope allows `directory.roster` at `SCH02` and nothing at `SCH04`

#### Scenario: Never outlives the parent
- **WHEN** the parent expires in 20 minutes and the approved lifetime is 2 hours
- **THEN** the minted mandate expires when the parent does

### Requirement: A supplementary mandate dies with its parent
The gateway SHALL refuse a mandate whose `parent` is revoked, with reason `PARENT_REVOKED`, and a mandate whose `parent` names a revocation list the gateway can't read, with reason `STATUS_UNAVAILABLE`.

#### Scenario: Parent revoked
- **WHEN** a parent mandate is revoked and the agent then uses the supplementary mandate minted from it
- **THEN** the gateway returns `403 DENY` with reason `PARENT_REVOKED`

### Requirement: An approved held call goes through once
When a request about a held call is approved, the minted mandate SHALL carry a `preapproved` claim, and SHALL expire no more than 5 minutes after approval. The claim contains the hash of that call's action: server, tool, canonical arguments, and the hash of the parent mandate. When a call with that mandate has an action hash in `preapproved`, and the gateway has no record of using that pre-approval, the gateway SHALL:
- skip the step-up hold for that call;
- decide it on every other check;
- record the pre-approval as used before forwarding.

Any other call SHALL be held as before. The record of used pre-approvals SHALL survive a gateway restart whenever the audit store is durable.

#### Scenario: Correction approved and applied once
- **WHEN** `pupil-data.write(pupil_id="P0011", urn="SCH04", column="FSMeligible", value="1", reason="...")` was held, the person approved a request naming its `decision_id`, and the agent retries the same call with the minted mandate
- **THEN** the gateway returns `200 ALLOW`, and the same call made again with that mandate returns `202 STEP_UP`

#### Scenario: Different arguments are held
- **WHEN** the agent uses the same minted mandate for `pupil-data.write` with `value="0"`
- **THEN** the gateway returns `202 STEP_UP`

### Requirement: Agents can't wear the person down
The gateway SHALL refuse a new scope request from a mandate that has 3 pending requests, or that has made 10 requests in the last hour, with reason `TOO_MANY_REQUESTS`. A request identical to one a person or supervisor rejected in the last hour SHALL be refused with reason `RECENTLY_REJECTED`; a request ended by a wrong number (`NUMBER_MISMATCH`) SHALL NOT count. These counts SHALL come from the store of scope requests, so they hold across gateway restarts.

#### Scenario: Asking again after rejection
- **WHEN** a request is rejected and the agent makes an identical request 5 minutes later
- **THEN** the gateway returns `403 DENY` with reason `RECENTLY_REJECTED` and no request is created

#### Scenario: Asking again after a wrong number
- **WHEN** a request ended with `NUMBER_MISMATCH` and the agent makes an identical request straight away
- **THEN** a new pending request is created, with a new number

### Requirement: Every approval step is recorded in the audit chain
The gateway and issuer service SHALL record these events into the audit hash chain, each referring to the scope request and, where there is one, to the `decision_id` of the call that created it:
- `approval_requested`;
- `approval_granted`, naming the approver and the `jti` of the minted mandate;
- `approval_denied`, naming the approver;
- `approval_expired`.

Events that happen on the issuer service, such as a person's decision, SHALL reach the same chain even if the agent never polls again.

A refused decision SHALL also leave a record:
- a supervisor's refused `grants.decide` is recorded as that call's own audit event;
- a person's refused decision (wrong key, no session, already decided) is recorded in the issuer's request log with its reason.

#### Scenario: Person can see who approved
- **WHEN** a request is approved by `officer:jsmith` and the minted mandate is used once
- **THEN** the audit events for the parent mandate include `approval_requested` and `approval_granted` naming `officer:jsmith` and the minted mandate's `jti`, and the minted mandate's events include the call
